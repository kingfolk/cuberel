# F6 fusion benchmark: Apple M1, 2026-11-09

On this machine and these workloads, fusion had a lower median completed-query
latency in all 14 final cases. The main workload improved by 3.45–5.47× on the
current CubeCL CPU path and 1.16–1.93× on native Metal. This compares the two Cuberel
plans; it is not a comparison against an optimized Rust/Arrow CPU implementation.

## Environment and measurement

- Apple M1, 16 GiB RAM, macOS 15.5.
- Rust 1.99.0 (`b940084d7`); Cargo release profile, debug assertions disabled.
- F6 library commit `154d2b1`; the accompanying benchmark example is a local addition.
- Pinned CubeCL `5037c0639ce3b1205392bdbe43dcf25e2ea09e29`.
- Default executor tiles: CPU 8 lanes, native Metal 64 lanes; unchanged per runtime.
- One immutable resident batch uploaded before measuring; query prepared beforehand.
- Timer covers `execute_pipeline(...).materialize()`: host plan validation,
  allocations, submissions, actual device execution, synchronization, error checks
  and scalar readback. Source upload and first compilation are excluded.
- Two warm-up pairs per case. Each timed mode has 7 samples on CPU and 31 on Metal.
  Mode order alternates each pair. CPU and Metal runs are sequential.
- Every result is checked against independent host iterator expectations, including
  participating row count and all five scalars. No kernel definitions occurred
  during timed samples. The "on" mode is `Required`, preventing silent fallback.
- Reported speedup is off-median / on-median. Raw samples and min/max are retained;
  these short local runs are not confidence intervals or a controlled lab study.

## Main workload

```text
x[i] = i % 1000
valid[i] = (i % 10 != 9)  // 10% NULL
WHERE x >= 500
COUNT(*), COUNT(x), SUM(x), MIN(x), MAX(x)
```

The threshold targets 50% of the non-NULL domain; actual selected rows are about
45% of source rows after NULL filtering and partial end buckets. SUM(I32) returns
I64. Both modes read back 36 bytes per measured query for count/scalar states.

| Runtime | Rows | Selected | Off median ms | On median ms | Off / on | Launches off → on |
|---|---:|---:|---:|---:|---:|---:|
| cpu | 1,024 | 450 | 20.029 | 3.662 | 5.47× | 29 → 16 |
| cpu | 65,536 | 29,283 | 368.643 | 106.757 | 3.45× | 41 → 26 |
| cpu | 1,048,576 | 471,669 | 5733.619 | 1518.644 | 3.78× | 47 → 31 |
| metal | 1,024 | 450 | 0.800 | 0.689 | 1.16× | 17 → 6 |
| metal | 65,536 | 29,283 | 0.852 | 0.713 | 1.20× | 23 → 11 |
| metal | 1,048,576 | 471,669 | 3.109 | 1.614 | 1.93× | 29 → 16 |

The million-row Metal case reduced median latency from 3.109 ms to 1.614 ms.
For 1,024 rows, launch reduction from 17 to 6 yielded only 1.16× median speedup;
fewer launches therefore do not translate proportionally into lower total latency. Large inputs
still need merge kernels, so fusion does not imply one launch for every size.
The CPU template is barrier-heavy; its large improvement does not establish that
it is competitive with a mature CPU aggregate implementation.

## Selectivity and checked-expression supplement

All cases below use 65,536 rows and the same NULL distribution. A target of 1%
means 585 selected rows; 100% means 58,983. The checked variant uses `x + one`
with parameter `one=1` for COUNT/SUM/MIN/MAX, retaining eager checked I32 rules.

| Runtime | Filter pass target | Argument | Off median ms | On median ms | Off / on | Read bytes off → on |
|---|---:|---|---:|---:|---:|---:|
| cpu | 1% | x | 375.620 | 96.261 | 3.90× | 36 → 36 |
| cpu | 100% | x | 364.154 | 102.398 | 3.56× | 36 → 36 |
| cpu | 1% | x + 1 (checked) | 383.006 | 93.077 | 4.11× | 9396 → 262180 |
| cpu | 50% | x + 1 (checked) | 397.031 | 95.164 | 4.17× | 468564 → 262180 |
| metal | 1% | x | 0.820 | 0.686 | 1.20× | 36 → 36 |
| metal | 100% | x | 0.851 | 0.699 | 1.22× | 36 → 36 |
| metal | 1% | x + 1 (checked) | 1.062 | 0.819 | 1.30× | 9396 → 262180 |
| metal | 50% | x + 1 (checked) | 1.225 | 0.867 | 1.41× | 468564 → 262180 |

For sparse checked expressions, fusion reads one original-capacity error plane
(262,144 bytes), while the reference reads four compact argument error prefixes
(4 × 585 × 4 = 9,360 bytes). Including scalar/count states, this is 262,180 versus
9,396 bytes. Despite the extra readback, fusion is faster here. The fused plan
avoids selection compaction and repeated argument evaluation/launches; the
benchmark does not isolate each cost. This is a measured tradeoff, not evidence
that fusion universally reduces transfer bytes.

At the 50% checked threshold, four compact error prefixes instead total 468,528
bytes, so sharing the fused error plane also reduces explicit readback bytes.

## Variation and limits

An initial 7-sample Metal pilot is retained as `phase=pilot` in the CSV. Its main
speedups were 1.16×, 1.14× and 1.96×; the final 31-sample run gave 1.16×, 1.20× and
1.93×. Absolute small-batch latency varied between runs, so the tiny-case advantage
should be read as a local median trend. No isolation from normal OS background
activity, thermal control or kernel-only GPU event timing is claimed.

This tests eligible I32 aggregate fusion over warmed resident data. It does not
measure cold compilation/upload, projection output, SQL parsing, other hardware,
or filtered F32 SUM (which deliberately cannot fuse under the current policy).

## Reproduce

```sh
CARGO_TARGET_DIR=/private/tmp/cuberel-fusion-target \
  cargo build --locked --release --all-features --example bench_pipeline_fusion

# Binary path below assumes the target directory above.
/private/tmp/cuberel-fusion-target/release/examples/bench_pipeline_fusion cpu 1024,65536,1048576 7 50 plain
/private/tmp/cuberel-fusion-target/release/examples/bench_pipeline_fusion metal 1024,65536,1048576 31 50 plain

# Repeat sequentially for each runtime; CPU uses 7 samples, Metal uses 31.
/private/tmp/cuberel-fusion-target/release/examples/bench_pipeline_fusion cpu 65536 7 1 plain
/private/tmp/cuberel-fusion-target/release/examples/bench_pipeline_fusion cpu 65536 7 100 plain
/private/tmp/cuberel-fusion-target/release/examples/bench_pipeline_fusion cpu 65536 7 1 checked
/private/tmp/cuberel-fusion-target/release/examples/bench_pipeline_fusion cpu 65536 7 50 checked
```

The example writes CSV summaries to stdout and individual samples to stderr.
[Summary CSV](fusion-m1-2026-11-09.csv) includes sample counts, ranges, launch and
readback counts; [raw samples](fusion-m1-2026-11-09-samples.csv) include every timed
observation, including the initial Metal pilot.
